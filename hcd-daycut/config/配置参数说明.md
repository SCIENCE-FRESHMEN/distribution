# 配置文件说明与仿真评分参数

本目录的运行配置包括三个文件：`warehouse.json` 定义仓库、策略和评分规则；`time_estimator.json` 定义堆垛机路径与作业时间；`sku_config.json` 是 API 专用的 SKU/BOM 配置。三个文件都可按 JSONC 读取，可保留 `//` 注释。修改 `warehouse.json` 或 `time_estimator.json` 后，API 必须重启；命令行仿真必须重新启动，修改才会生效。`sku_config.json` 可在启动前直接维护，也可由 BOM 更新接口在运行期间更新。

## `sku_config.json`

该文件是 API 服务启动时的初始 BOM 配置，初始内容应保持为空对象和空列表。命令行仿真仍默认读取 `simulation/data/sku_config.json`，因此修改本文件不会改写仿真用 BOM。启动 API 前可直接编辑并保存；服务已经运行时，推荐调用 `POST /api/v1/bom/update` 传入完整配置，服务会立即刷新核心、入库巷道分配器和货位分配器中的 BOM 缓存，并写回本文件。

| 参数                       | 类型       | 含义和约束                                                                                                                                                                       | 示例                                           |
| -------------------------- | ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| `sku_types`              | 字符串列表 | 系统已知 SKU 列表。BOM 中出现的每个 SKU 都应列出；                                                                                                                               | `["2801022-TG152", "2801038-TG152","A","B"]` |
| `sku_pairs`              | 对象       | 双层纵梁配对表，键和值均为 `skuId`。不同 SKU 的配对必须双向填写；同 SKU 自配对可写为自身。不参与配对的 SKU 不应写在此表中。                                                    | `{"A": "B", "B": "A", "A1": "A1"}`           |
| `sku_solo`               | 对象       | 单梁 SKU 标记表，键为 `skuId`，值为 `true`。此类 SKU 不能与其他 SKU 组成双梁上下层位置。                                                                                     | `{"C": true,"D",true}`                       |
| `sku_to_production_line` | 对象       | SKU 到可服务产线的映射，键为 `skuId`，值为产线号字符串列表。一个 SKU 可供多条产线使用。缺少某 SKU 映射时，调用方会按任务显式产线或默认逻辑处理，不应依赖缺失映射表达服务范围。 | `{"A": ["1", "2"]}`                          |

一个最小双梁 BOM 配置如下。`A` 与 `B` 的双向关系用于入库时判断天然配对位置、出库时验证同一双层货位；若二者还需要区分版本、属性等条件，则由 `warehouse.json` 的 `match_fields` 同时约束。

```jsonc
{
  "sku_types": ["A", "B", "C"],
  "sku_pairs": {"A": "B", "B": "A"},
  "sku_solo": {"C": true},
  "sku_to_production_line": {
    "A": ["1"],
    "B": ["1"],
    "C": ["2", "3"]
  }
}
```

当 `sku_types` 为空时，API 可以启动，`GET /api/v1/bom/config` 会返回空配置；但包含未识别 SKU 的入库请求会被拒绝并返回 `invalidSkus`，不能据此生成入库或出库任务。配置完整 BOM 后，须保证已经进入系统的库存和任务与新 BOM 关系一致；运行中切换 BOM 不会自动重排既有库存或已冻结任务位置。

## `warehouse.json`

该文件由 `WarehouseCore` 加载，同时影响 API 和命令行仿真。数值参数中的时间单位均为秒；除明确说明外，时间、数量和容量都应为非负数。

| 参数                                | 类型       | 含义和使用范围                                                                                                                                                    | 例子                 |
| ----------------------------------- | ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------- |
| `num_aisles`                      | 整数       | 巷道数量。决定库存、任务调度和 API `aisleStatus` 的巷道集合。必须大于 `0`。                                                                                   | `5`                |
| `num_production_lines`            | 整数       | 生产线数量。系统初始化 `1` 到该值的生产计划、生产组进度和巷道拥堵状态。                                                                                         | `3`                |
| `aisle_production_line_mapping`   | 对象       | 键为巷道号字符串，值为可服务产线号整数列表。必须显式覆盖所有巷道；具体缺失键行为见下文。                                                                          | `{"1": [1, 2, 3]}` |
| `num_rows`                        | 整数       | 每巷道排数。纵梁库通常为 `2`，内部行号 `1`、`2` 对应左右两排。                                                                                              | `2`                |
| `num_columns`                     | 整数       | 每排列数，影响货位数量和行走距离。                                                                                                                                | `3`                |
| `num_levels`                      | 整数       | 每列层数，影响货位数量、行走距离和优选层位。                                                                                                                      | `18`               |
| `position_column_preference_mode` | 整数       | 同等可行且路径成本相同的货位列号择优方式：`1` 最小列优先，`2` 中间列优先，`3` 最大列优先；也用于 FIFO 出库入库时间相同的候选排序。默认 `3` 保持既有行为。 | `3`                |
| `initial_inventory_count`         | 整数       | 仅命令行仿真：从历史入库记录取多少条构造初始库存。API 由请求中的 `inventory` 同步库存，不使用此值。                                                             | `200`              |
| `disabled_positions`              | 字符串列表 | 禁用货位坐标，格式为 `巷道-排-列-层`。不影响仓库几何，但不会作为入库或移库空位返回。                                                                            | `["1-1-1-1"]`      |
| `use_magnetic_crane`              | 布尔       | 是否启用磁力吊时间和左右库资源逻辑。                                                                                                                              | `false`            |
| `outbound_congestion_time`        | 浮点数，秒 | 仿真中一次出库完成后，本地出库口暂时拥堵的时长。API 明确传入持续拥堵时不使用该值。                                                                                | `10.0`             |
| `transport_delay_s`               | 浮点数，秒 | 入库任务已分配巷道后，到达巷道入口的运输时长。                                                                                                                    | `30.0`             |
| `magnetic_crane_time`             | 浮点数，秒 | 启用磁力吊时一次动作的耗时。                                                                                                                                      | `40.0`             |
| `relocation_delay_s`              | 浮点数，秒 | 仿真中移库操作占用相关巷道的时长。                                                                                                                                | `80.0`             |
| `match_fields`                    | 字符串列表 | SKU 匹配时必须一致的属性字段名。空列表表示只按 `skuId` 匹配。                                                                                                   | `["version"]`      |
| `outbound_fifo_enabled`           | 布尔       | `true` 时，同 SKU、同属性的候选库存按最早入库时间优先出库。                                                                                                     | `false`            |

纵梁库固定为双排、双层货位结构，因此不再配置 `use_double_layer`。`total_positions` 由
`num_aisles × num_rows × num_columns × num_levels` 自动计算，`max_beams` 自动取该物理货位数的两倍；
这三项不应再单独维护，以免与仓库几何发生冲突。

### API 日志配置

`api_logging` 是 `warehouse.json` 顶层对象，仅在 API 启动时读取；命令行仿真不使用。修改任一字段后必须重启 API。相对目录以源码项目根目录或部署包中可执行文件所在目录为基准。

```jsonc
"api_logging": {
  "enabled": true,
  "directory": "logs",
  "file_name": "api.log",
  "max_file_size_mb": 10,
  "max_total_size_mb": 100,
  "backup_count": 20
}
```

| 参数                  | 类型     | 含义和约束                                                                                                   | 示例          |
| --------------------- | -------- | ------------------------------------------------------------------------------------------------------------ | ------------- |
| `enabled`           | 布尔     | 是否启用容量受限的 Uvicorn 文件日志。为 `false` 时不创建文件处理器，Uvicorn 使用自身默认控制台日志配置。   | `true`      |
| `directory`         | 字符串   | 日志子目录；相对路径从运行根目录计算。目录不存在时自动创建。                                                 | `"logs"`    |
| `file_name`         | 字符串   | 当前正在写入的日志文件名。应只填写文件名，避免与 `directory` 重复拼接。                                    | `"api.log"` |
| `max_file_size_mb`  | 数值，MB | 单个当前日志达到该大小后触发滚动。小于或等于零的值会在运行时收敛为最小正值，不建议这样配置。                 | `10`        |
| `max_total_size_mb` | 数值，MB | 当前日志与全部归档日志的累计大小上限。超限时按修改时间删除最旧归档，不删除当前 `api.log`。                 | `100`       |
| `backup_count`      | 整数     | 最多保留的归档文件数。滚动文件按 `api.log.1`、`api.log.2` 递增命名；总容量限制仍可能使实际数量小于该值。 | `20`        |

### 对象和列表参数

`aisle_production_line_mapping` 是“巷道号 -> 可服务产线号列表”的对象。JSON 键必须写为字符串，加载后转换为整数；值为整数列表。

```jsonc
"aisle_production_line_mapping": {
  "1": [1, 2, 3],
  "2": [1, 2, 3],
  "3": [1, 2, 3],
  "4": [1, 2, 3],
  "5": [1, 2]
}
```

该对象必须显式包含每个 `1` 到 `num_aisles` 的巷道。若整个参数不存在，系统才会默认“全部巷道服务全部产线”；但参数一旦存在，遗漏某个巷道不会补默认值。以 5 巷道为例，如果只写 `"1"`、`"3"`、`"4"`、`"5"`，遗漏的 2 巷道在改进巷道分配器中不会服务任何产线，部分直接按巷道号读取映射的旧路径还可能发生键不存在错误。因此不能通过省略键表达“巷道 2 服务全部产线”，应明确写为 `"2": [1, 2, 3]`。若希望某巷道不服务任何出库产线，可写 `"2": []`；该巷道仍可存在，但不会被带产线约束的出库或入库任务选中。

`disabled_positions` 是禁用货位字符串列表，每项格式为 `巷道-排-列-层`：

```jsonc
"disabled_positions": ["1-1-01-01", "3-2-03-09"]
```

禁用位仍属于仓库几何，但不会作为入库或移库空位返回。`row` 必须是内部行号 `1` 或 `2`；列、层非2位数可补零，也可使用例如"3-2-3-9"表示。坐标应落在 `num_aisles`、`num_rows`、`num_columns`、`num_levels` 范围内。

`match_fields` 是 SKU 属性字段名列表。非空时，入库任务、出库任务和库存位置的同名属性都必须相等，才允许 SKU 匹配、配对或出库：

```jsonc
"match_fields": ["version", "productionAttribute", "militaryCivilianMark", "salesArea"]
```

对应 API SKU 示例如下：

```json
{
  "skuId": "2801022-TG152",
  "quantity": 1,
  "version": "00",
  "productionAttribute": "D",
  "militaryCivilianMark": "M",
  "salesArea": "N"
}
```

`[]` 表示只按 `skuId` 匹配。不要写 `""` 作为字段名；若不需属性匹配，应使用空列表。

API 的下游拥堵也与本文件的巷道-产线映射相关，但它是每次 `POST /schedule/mixed` 传入的动态状态：

```json
{
  "aisleId": "1",
  "isAvailable": true,
  "unavailableReason": null,
  "bank": "LEFT",
  "exitCongestion": [
    {"lineId": "1", "isCongested": true},
    {"lineId": "2", "isCongested": false}
  ]
}
```

`isCongested: true` 会持续阻塞该“巷道 × 产线”组合，直到同一组合后续明确传入 `false`。如果一条产线有多个可服务巷道，必须将这些巷道都标记为拥堵，优化器才会将该产线视为完全受阻，并将其排除出产线进度平衡方差。

### 仿真评分参数

以下权重只在 `scheduler_type: "optimization"` 时生效。候选方案先在独立的仓库副本中仿真，分数越小越好：

```text
评分 =
  makespan_weight × makespan
  + balance_weight × max(0, balance_before - balance_after) × 1000
  + production_line_avg_time_weight × avg_production_line_time
  + production_line_balance_weight × Var(line_progress)
  + aisle_dispersion_weight × Var(aisle_task_count)
  + inbound_wait_weight × inbound_wait_time
  + 100 × Var(expected_line_progress) [P95大致在2.0]
  - outbound_choice_bonus_weight × Σ log(每项任务的直接出库位置数)
```

各权重参数推荐值如下表所示：

| 参数                                |    当前值 | 建议范围              |  推荐起点 | 说明                                                                                                                                                                                                 |
| ----------------------------------- | --------: | --------------------- | --------: | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `lr_balance_weight`               |  `0.05` | `0.00` 到 `0.20`  |  `0.05` | 只改变库存均衡度原始量中左右库均衡部分的占比，随后再经 `balance_weight` 计入总分；没有独立的 P95 评分值。                                                                                          |
| `makespan_weight`                 |  `0.01` | `0.001` 到 `0.05` |  `0.01` | 主要指标：本轮整体完工窗口。两种策略取中间量级后，P95 约 `300s`，当前权重下约贡献 `3.00` 分。                                                                                                    |
| `balance_weight`                  |  `0.10` | `0.10` 到 `1.00`  |  `0.10` | 仅惩罚库存均衡变差，不奖励改善。P95 原始惩罚约 `3.60`，当前权重下约贡献 `0.36` 分。                                                                                                              |
| `production_line_avg_time_weight` |  `0.01` | `0.01` 到 `0.05`  |  `0.01` | 各产线最后一个出库任务的平均完成窗口。P95 约 `185s`，当前权重下约贡献 `1.85` 分。                                                                                                               |
| `production_line_balance_weight`  |  `0.01` | `0.01` 到 `1.0`   |   `0.5` | 产线进度平衡项，受传入的产线计划长度相关，越长影响越小，取值建议越大，API模式一般较短，故推荐小值。                                    |
| `aisle_dispersion_weight`         |  `0.50` | `0.05` 到 `2.0`   |  `0.50` | 值越大表示任务数量越集中于少数巷道；提高权重会更倾向均分巷道任务。P95 原始值约 `0.5`，当前权重下约贡献 `0.25` 分。                                                                               |
| `inbound_wait_weight`             | `-0.01` | `-0.05` 到 `0.05` | `0.001` | 当前负值会使等待时间越长总分越低，即奖励入库等待；如目标是惩罚等待，应改为非负值。P95 约 `250s`，当前权重下约贡献 `-2.5` 分。                                                                    |
| `outbound_choice_bonus_weight`    |   `1.0` | `1.0` 到 `5.0`    |   `1.0` | 正权重产生负分奖励，鼓励保留多个直接出库位置。P95 为 `0`，说明仅少数候选获得奖励(因为log1=0)；已获得奖励的候选最低约为 `-6.3` 分。                                                               |

注：P95为所有数值从小到大排序后，95%的样本值所对应的位置。

## `time_estimator.json`

该文件由 `TimeEstimator` 加载，决定路径物理时间和固定取放货时间。它不会改变任务可行性或配对关系，但会影响任务预计完成时间、`makespan`、平均产线完成时间、巷道占用和最终评分；纵梁库改进货位策略还会使用其中的二维物理参数，在候选空位和非天然双梁对侧空位之间比较实际列/层移动时间。

| 参数                    | 类型       | 含义与范围                                       | 例子     |
| ----------------------- | ---------- | ------------------------------------------------ | -------- |
| `pickup_time_default` | 浮点数，秒 | 一次取货固定耗时，应大于等于 `0`。             | `17.0` |
| `drop_time_default`   | 浮点数，秒 | 一次放货固定耗时，应大于等于 `0`。             | `17.0` |
| `dock_in_col`         | 整数       | 入库口列号，必须在 `1` 到 `num_columns` 内。 | `1`    |
| `dock_out_col`        | 整数       | 出库口列号，必须在 `1` 到 `num_columns` 内。 | `3`    |

`dock_map_in` 和 `dock_map_out` 均为“编号（出入库口编号） -> 层号（仓库真实层）”的对象，键和值在加载时转换为整数。同样需要保证后期输入的出入库口编号存在于 `dock_map_in` 和 `dock_map_out`：

```jsonc
"dock_map_in": {"1": 1, "2": 5, "3": 9},
"dock_map_out": {"1": 1, "2": 11, "3": 16}
```

当前估时流程在初始化路径和任务路径中都会查询这两个映射。若某次查询的编号不在字典中，会使用默认层 `1`，不会报错，但估算路径可能偏离真实出入口。因此新增入库线、产线或实际出入口层位时，应显式补充对应键，不建议依赖默认层。层号必须在 `1` 到 `num_levels` 内。

`physics` 是堆垛机物理参数对象：

```jsonc
"physics": {
  "col_scale": 15.0,
  "layer_scale": 0.5,
  "v_col_max": 1.5,
  "v_layer_max": 0.625,
  "a_col": 0.15,
  "a_layer": 0.075
}
```

`col_scale`、`layer_scale` 是相邻列、相邻层距离，单位米；`v_col_max`、`v_layer_max` 是最大速度，单位米/秒；`a_col`、`a_layer` 是加速度，单位米/秒平方。六个值都应大于 `0`。应以实测运行时间校准这些参数；仅通过减小距离、增大速度来降低仿真分数会使仿真结果失真。

改进货位策略初始化时先计算“移动一列”的物理时间，再用二分查找得到在该时间内可连续升降的最大层数，记为 `levels_per_column`。每个候选随后仅计算 `列差 + 层差 / levels_per_column` 的列等价加权曼哈顿距离，而不重复运行完整的加减速模型。该比例按连续升降计算，不会把单层启停时间重复叠加；因此当列方向较慢、层方向较快时，策略可能优先同列的不同层，反之则可能优先同层的相邻列。`position_column_preference_mode` 仅在加权距离相同后用于消除并列。
